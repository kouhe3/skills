# E. 驱动、自动化与状态判定

| 症状 | 机制 | 规则 |
|---|---|---|
| 「点了没反应，说明按钮坏了」 | 驱动通道不支撑（合成消息不触发，真实输入同坐标立刻生效） | 先做**阳性对照**（已知必然生效的最小动作），再谈被测对象 |
| 「定时点击落在启动动画里，不是主菜单」 / 「state=menu after 0.1s」 | 启动动画/加载期占掉几十秒；屏幕分类器会把 loading/intro 误报成 menu，固定延时也落空 | 状态判定**优先读进程内状态字段 / 日志 / API**；屏幕锚点只作关卡内 UI 的兜底；用状态转移门控输入，判定不出来返回 `unknown` |
| 「进关/换关只能靠鼠标点」 | 状态转移由命令枚举的分发器完成，点击与画面只是末端表现；屏幕分类会把 loading 误报成 menu，坐标还受缩放与前台状态影响 | 先找 state machine 与 command enum：**调用序驱动转移、内存字段读状态**；输入自动化降为阳性对照与光标驱动玩法的通道，不再当主驱动——它产出的通道知识（合成消息是否生效、坐标缩放、按下采样窗口）仍要落账 |
| 「悬停高亮了，点击应该也生效」 | 输入按帧轮询；瞬时 down/up 落在两帧之间，位置对也无效 | 按下保持 ≥150 ms 再抬起；悬停只证明坐标对，不证明按下被采样 |
| 「脚本跑两次结果一样，就是确定性输入」 | 只证明可重复，不证明可复现任意输入 | 要**录下输入再重放**才叫 harness；时序一改，结论就变 |
| 「游戏自己退了 / 崩了」 | 可能是探针超时清理把 debuggee 杀了 | 先查退出路径：超时 job 的强制结束、探针 `finally` 清理；排除仪器再说被测对象 |
| 「API 返回成功，值就是 0」 | 绑定未声明 `restype/argtypes`，64 位值被截成 int | 两个系统 API 双双恒 0（一个让 CPU 永远 0%、一个让 DPI 永远 unaware）；恒 0 / 恒空先怀疑绑定声明 |
| 「`GetProcAddress` 返回空，说明 DLL 缺失」 | Lua 5.1 的 `lua_setglobal` 是宏、不是导出符号；很多 API 是宏/内联/版本差异 | 分开打印 `LoadLibrary` 结果/错误码与每个符号的 `GetProcAddress`；宏改用底层函数（`lua_setfield(L, LUA_GLOBALSINDEX, …)`）；「dll=missing」的结论要能区分这两种失败 |
| 「采集失败也算一关不一致」 | 一关一进程的 dispatch 偶发超时（主线程忙/窗口状态），与关卡内容无关 | 采集失败单独分桶（ERROR），瞬时失败**重试**并把重试次数写进出处；一致率只统计成功采集（实例：某关一次 dispatch 20 s 停在 menu，重试后成功） |
| 「鼠标拖不动，先怀疑对象」 | 坐标/DPI/y 轴/前台/按键采样任一不对都表现为「对象没反应」 | 先出**标定图**（刚体/目标/轨迹），标注点压住实际对象；前台与按键状态各给一条读数，再谈拖动 |
| 「脚本卡在截图/日志，鼠标根本没动」 | 控制回路里放了全量 FFI 日志解析或截图；工具还没走到输入 | 状态回读用每步小 digest + live flush；截图放阶段之间；控制回路延迟写进用法 |
| 「硬编码轨迹跑一次失败，说不清是对象还是通道」 | 开环输入；坐标与状态都没有回读 | 改成闭环：读 body→算光标→按住→重读；标定 claim 与行为 claim 分开预注册 |
| 「内存写了 target/按键，力却没跑」 | 这些字段由引擎输入循环每帧刷新；外部写与输入循环竞态，按键/目标被清零 | 先证明字段保持（写→等→读回）；保持不住就改进程内 API/代理注入，不要和输入循环抢 |
| 「level state 已到，完成态却退回主菜单」 | `level state` 先于菜单关闭/场景切换；控制器立刻 action 会绕过异步 settle | 等 0.5–1 s，复查 level+menu+控制器 armed 后再 action；把 settle 作为 claim 的前置 |
| 「物理上已到目标，Level complete 对话没出现」 | UI 完成是延迟状态（2.5 s 计时、烟花、菜单关闭），不是物理事件的同义词 | 物理完成与 UI 完成分两行判；UI 轮询/等 settle，采样过早会假阴性 |
| 「PD 力推得慢/顶在箱壁上」 | 施力点、碰撞与力上限共同决定；质心施力可能顶墙，速度伺服/waypoint 更快 | 先量接触与施力点；力模式与速度模式各自 A/A/负例，不混表 |
| 「实机 A/B 里物体自己在动」 | 启动器还开着**脚本驱动力**（固定点磁铁 / 自动拖拽开关），与真实输入模式互斥；不是物理 bug | 手动 A/B 前先打印/隔离启动开关白名单；脚本输入与真实输入各走一条通道，不同时开；自走异常先查开关再改模型 |
| 「`ab` 进真模态后控制通道拿 busy / 挂死」 | 命令在 UI 线程同步执行且持 busy 锁，模态循环期间收不到命令；跨线程 `EndDialog` 也不安全 | 模态驱动放进程内独立线程，`WH_CBT` / `EnumThreadWindows` / `GetGUIThreadInfo` 找框，`BM_CLICK` / `WM_COMMAND` 关框，带 deadline + force close；比较 `EndDialog` nResult 与控件树（instruments §0.9） |
| 「对话框里填的数字被改回原值」/「S 的 tpl 是空、`ord=5400`」 | 填控件早于 `WM_INITDIALOG` 会被 proc 初始化覆盖；`DialogBoxParamW` 的模板参数 > `0xFFFF` 才是字符串指针，裸 RVA 会被当序号并静默走 canned | 用「对话框可见 + 控件存在」门控填值；按调用序号给值；S 传与 oracle 同类模板参数，环里 `tpl/ord/proc/parent/init/ret` 逐项比（instruments §0.9） |
| 「同一 oracle 跑两遍，第二遍 GDI 多了上百个 op」 | A/B 进真模态后，对话框消息循环把上一条 case / 上一 pass 的更新区画出来 | 每 pass 开始先 `ValidateRect(hwnd,NULL)` 清更新区，再让函数自己制造更新区（instruments §0.9） |

| 「两侧事件流 0/0，判据通过」 | 目标分支在两侧都没被走到：点击没命中、提示框没弹、命令被静默忽略，两条空流自然相等 | 比较前先断言**效果见证**（box 数 / 事件条数 / `s_calls>0` / 目标控件 id）；见证失败直接 FAIL，不把 0/0 当证据 |
| 「私有桌面里 `GetCursorInfo` 看不见光标 / `PostMessage` 返回 `ERROR_INVALID_WINDOW_HANDLE`」 | 窗口句柄按桌面生效，跨桌面投递被拒；全局光标查询只反映活动桌面 | 输入与观测都在**目标进程内部**（控制通道命令 / 进程内 hook）；光标按**身份**分类（与进程内新加载的 stock/app 光标比对），不比较句柄值 |
| 「`PostMessage(hwnd, WM_COMMAND, IDOK, 0)` 之后框还挂着」 | `MessageBox` 的模态循环只认按钮通知，直投 `WM_COMMAND` 不结束对话框 | 找到按钮 `BM_CLICK`（带 `SendMessageTimeout` 与 deadline/force close），关闭后核对 `dialog_open/close` 与控件树；命令返回 ok ≠ 框已关 |
| 「取消路径的状态和确认路径一样，说明没分歧」 | 静默与报警是两条路径：状态可能相同，事件流/旁路不同（取消不弹框，错误实现多弹一个） | 状态等价 ≠ 等价；事件流与旁路差异同样 FAIL，负例覆盖「只改旁路、状态不变」的变异 |
| 「一次按键注出两个字符 / 两步动作」 | 注入的 `WM_KEYUP` lParam 缺 transition/previous-state 位（实测 `1` vs `0xC0000001`）：`TranslateMessage` 会把 KEYUP 再翻成一个 `WM_CHAR`，数字键因此重复执行 | 注入与真实消息同形（KEYUP 用 `0xC0000001` 或框架标准值）；把**每条按键命令的 WM_CHAR 计数**做成仪器自检（1 次按键 = 1 字符，非数字键也数），否则双击路径会重复执行且难归因 |
| 「300 ms 窗口里的中间状态总抓不到」 | 轮询周期大于窗口，50 ms 采样靠运气；两次独立采集自然对不上 | 短窗口观测与触发**合并进同一 UI 事务**（键后立即 mousemove / 立即读环），或用环记录；PASS 断言「环里出现过该记录」，不要用 poll 采样当判据 |
| 「Yes 之后要点的第二个框，结果 id 2 打到了上一个框」/「按 pid 取最上层 `#32770`」 | 两级模态串行出现；只按进程取 topmost 会把命令投给残留 / 错误的框，`posted=true` 只证明某个框收到了消息 | 驱动步按**标题 / 控件**过滤目标框，并断言每步 `posted`；两级框各留 `dialog_open/close` 事件；找不到目标就 FAIL，不静默投 topmost |
