# 个案库：症状 → 机制 → 规则

这是**规则库**，不是事故日志：每行是一个可复用的判断。症状列是可检索的触发词（写成你脑子里闪过的那句话），机制列解释为什么会被骗，规则列说下一次怎么做。规范在 `SKILL.md`，claim 形状在 `claims.md`，仪器做法在 `instruments.md`。

**可移植**：行里的 `F##`、资产名、关卡编号来自案例项目，只作溯源；换项目时映射到你自己的对应物，不把案例绑定带进判据。规则本身只写相对约定。

## 分诊：先判是哪一类错

卡住时先过七问，再进分区；只读命中的分区。

| 问 | 危险信号 | 先查 |
|---|---|---|
| 目标分支真的执行了吗？ | 没执行：0/0、hit=0、no-op 语料都是假绿 | A、E |
| 坏实现也会得到同样的 0 / 终态吗？ | 会：比较面漏了副作用、旁路或过程计数 | A |
| 测量窗口的起点在动作之前吗？每 pass 复位了吗？ | 否：基线错位、stale 环、一次性 API 都会伪装成实现差 | A、I |
| 分子与分母、两侧的地址 / 句柄 / 单位可比吗？ | 否：归一化或坐标系混用 | A、C |
| 语料从代码 / 数据枚举，还是从实现的分支假设来？ | 后者：覆盖度不是等价性 | A、`coverage-domain.md` |
| 阳性对照过了吗？仪器版本与当前产物一致吗？ | 否：仪器没接上，先修仪器 | A、`instruments.md` §0.2 |
| 报告里的数字能从源头重算吗？ | 否：派生数字手抄、口径混用 | A、`claims.md` |
| 两版实现 / 两棵树对不上？ | 差异可能全无行为影响；相似度被重定位糊住 | G |
| 这个未知该问谁？ | 机制问题问用户 / 用户答「不知道」就停 / 猜测进 glossary | A |

## 用法与准入

- **按需查，不通读**：分区按检索时机划分，不按重要程度；分诊后只读相关分区，`grep` 症状列关键词，读命中的行。症状在遇到它之前认不出来，开工前通读是浪费。
- **合并优先**：新增前先 `grep` 机制列；已有机制能覆盖 → 把新症状并进那一行的症状列（` / ` 分隔），不新增行。
- **一行一机制**：只写最决定性的机制；其余进指针。两个都决定性 → 拆两行。
- **规则可执行**：写「下一次做什么」，不写故事；规范已在别处写过的，只写触发条件 + 指针，不复述全文。
- **晋升阶梯**：同一机制第 2 次出现 → 升成清单项（`instruments.md` §1 或 `SKILL.md` 的检查表）；第 3 次 → 升成规范。晋升后本行只留「症状 → 规范指针」，规则正文归规范，别处不留副本。
- **答不出就不收**：写不出「不看这条会做错什么」→ 不进库。
